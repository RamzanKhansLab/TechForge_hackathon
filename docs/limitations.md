# Limitations and operational boundaries

- Public GitHub work is incomplete. Private repos, employer code, offline projects, forks, and archived repositories are excluded. Ownership does not prove authorship; a supplied username does not establish identity.
- Up to two pages of 100 recently pushed repositories are considered; by default six eligible repositories are inspected. The tree is limited to 5,000 entries, with at most ten bounded content reads per repository and twenty retained signals per skill/type within each repository. Monorepos, vendored files, unusual manifests, and deep project structures can be missed.
- GitHub language data can include generated/copied code. Dependencies may be unused. README statements may be stale. No source execution, code quality audit, or test execution occurs.
- Commit metrics describe at most 100 author-filtered commits on the default branch. `firstCommit` is the earliest sampled commit, not necessarily the candidate's first contribution. Author association is GitHub's metadata and is not independent identity verification.
- Deployment config, CI files, and README links are identified as signals. A config file or a listed URL does not confirm a live deployment, successful CI, or production operation. The service does not visit arbitrary README URLs.
- PDF parsing requires a readable, unencrypted text layer and supports up to 15 pages. There is no OCR. Column layouts, heading variations, contact data, and resume sections may parse imperfectly. The skill dictionary can miss synonyms or match ambiguous short terms.
- Required/preferred extraction is deterministic, not semantic understanding. Mixed clauses, negation, and headings can be misclassified. Users can inspect the original job description; a skill-editing workflow is outside this MVP.
- Skill Coverage is not a hiring prediction, ranking, competency assessment, or fairness certification. Humans must consider broader context.
- GitHub requests are rate limited. Per-process caching may keep public metadata for up to 15 minutes; new reports can reuse those responses. A rate-limited analysis fails visibly for retry. Optional missing metadata is disclosed through repository warnings.
- Render free instances sleep/restart. MongoDB leases preserve recoverability but cannot guarantee immediate or uninterrupted background execution. The single-process worker bounds concurrent analysis; queue latency grows with traffic.
- In-memory API caches and rate limits are not shared across instances. Horizontal scaling needs shared rate limiting and operating limits even though MongoDB claims prevent most duplicate ownership.
- Access keys are bearer capabilities stored in browser localStorage, not user accounts. Clearing storage loses access without a backup; there is no password reset, revocation UI, or token rotation. An XSS vulnerability would expose browser-held keys. CORS is not an authorization boundary.
- Resumes and extracted personal data persist until explicitly deleted. No automated retention, account-level audit, billing, organization policy, or formal compliance program is implemented.
- An interrupted upload between Cloudinary acceptance and MongoDB creation can leave an orphan asset. Normal failures use rollback, but process death cannot execute cleanup. Periodic provider-side reconciliation is an operational responsibility.
- Cloudinary deletion, linked-job deletion, and candidate deletion span providers and are not one transaction. Delete the media first and retry on failures; a failure after media deletion can leave metadata awaiting another deletion request.
- A creation response lost after persistence can create an inaccessible report because only the creation response contains its access key. Idempotent upload ownership and account-backed recovery are future improvements.
- No tests, browser automation, load benchmarks, or live cloud deployment are bundled. Build/syntax validation does not establish end-to-end production readiness.
